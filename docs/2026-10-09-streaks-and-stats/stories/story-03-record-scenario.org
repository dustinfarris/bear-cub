#+begin_quote
The gate reviews the record screen in four states; one scenario call stages each exactly, so no state is hand-staged through ~project_eval~. ~record(state)~ deletes the completions dated before today for the first two kids (by id) and seeds backdated completions on their existing routine chores so that, with ~open(:morning)~ and no completion today, the screen shows:

| State | Kid 1 (current / longest)                                 | Kid 2 (current / longest)                                                  | Checks                                                      |
|-------+-----------------------------------------------------------+----------------------------------------------------------------------------+-------------------------------------------------------------|
| ~:a~  | 12 / 19                                                   | 3 / 3                                                                      | normal; Kid 2 carries =Best ever!=                          |
| ~:b~  | 0 / 19 (last night's evening left undone, so today is ~:failed~) | 6 / 9                                                                      | reset: dashed flame, =0=, =Start again today!=, longest tile unchanged |
| ~:c~  | 12 / 19                                                   | 4 / 4, first completion in the previous calendar month (two months shown)  | few-months chart: two wide bars, no gridlines               |
| ~:d~  | 112 / 118                                                 | 104 / 104                                                                  | three-digit streaks and four-digit lifetime totals fit      |

Seeded runs are separated by single missed days; history spans at least 8 months in ~:a~, ~:b~ and ~:d~ so the full chart renders. Lifetime figures follow from the seeded completions and the kids' chore values; they are not pinned. Today's completions are left alone, so the scenario pairs with ~reset/1~ and ~open/1~. Deleting past completions destroys the dev database's history, which no scenario has done before; it is dev-only and accepted for staging. Add the scenario to ~test/bear_cub/dev/scenarios_test.exs~ (assert each state's current/longest through ~Streaks.by_kid/2~), the moduledoc usage list and the CLAUDE.md scenario list.

Screenshots of this screen carry the kids' names in both banners. Until the review-mask scenario on the backlog exists, hide them in the page before capturing, per CLAUDE.md's household-data rule.
#+end_quote

* User Story

As the person reviewing the kiosk before a deploy, I need one call per record-screen state that seeds exactly the streak history that state needs, so that every state the gate asks for can be staged on the running dev server without hand-writing completions.

- In tests, "morning window open and no completion today" means today is pending, so pin the window with ~put_windows/2~ (~test/support/schedule_helpers.ex~); in dev, pair with ~open(:morning)~.
- Running ~record/1~ through Tidewave ~project_eval~ deletes the dev database's real past completions for the first two kids. Warn the human before the first run, and run it through ~project_eval~ so broadcasts land in the running server (CLAUDE.md).
