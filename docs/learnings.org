#+title: Learnings
#+startup: showall

Things we learned building the MVP that are *not* recorded in commit
messages, CLAUDE.md, or the PRD/design docs. Newest entries at the top
of each section are fine; every entry carries the date it was learned.

* [2026-10-07 Wed] A verification line that names a staged state is checked against the scenario that stages it
The night-owl-bonus DESIGN asked the gate for a screenshot of "one kid earned, one not" and, a page earlier, designed ~Scenarios.night_owl/1~ to move every kid's cutoff after now, which stages an earned or an unfinished evening and never a late one. Story 03's note saw it coming, and the gate staged the late kid by hand through ~project_eval~, the hand-poke CLAUDE.md says scenarios exist to replace. When a DESIGN names a reviewable state (a gate screenshot, a story's visual DoD item) and a scenario meant to stage it, read the two together at promotion and make the scenario produce that exact state. A scenario that stages a neighbouring state leaves the gate hand-staging, and the hand-staged version is the one nobody can re-run. Evidence: docs/2026-10-05-night-owl-bonus/retro.org, Batch 1 ("The scenario could not stage the gate's own screenshot").

* [2026-10-04 Sun] Green tests, wrong code: prove the behavior an AC names, not the attribute meant to produce it
Effort-multiplier Story 09 exists because Story 08 shipped with ~mix precommit~ green and two behaviors broken. Its AC said the count panel scrolls into view, and its tests asserted that the ~phx-hook~ attribute was present on the element, not what it was set to. ~phx-hook~ there was an expression, and LiveView expands a dot-prefixed name (~.ScrollIntoView~) to the colocated hook's full name only in a literal, so the hook never loaded; the browser logged "unknown hook" and a panel opened on the fifth extra ended below the fold. Its other AC kept the panel's ground tinted rather than flooded with the kid's color, and the test checked the ground before the 280 ms confirm beat, while the render during the beat is what handed ~chore_card_style/5~ the ~@done?~ that flooded it. Both tests asserted structure where the AC described behavior.

An AC about a behavior is proved by the behavior: assert the value the hook resolves to (or drive it in a browser), not that the attribute exists, since an attribute that is present and wrong passes. An AC about a transient state is proved inside that state: put the test in the beat (the 280 ms confirm window) rather than on either side of it, because the before and after renders were both correct. Evidence: the Third insertion note in docs/2026-09-20-effort-multiplier/PLAN.org's Batch 1 LOGBOOK (the Story 09 insertion record), which also records that no D-entry or DESIGN edit followed, because the body was right and the code was wrong.

* [2026-09-06 Sun] Gate on a local kiosk review; the tablet check was later made optional
The on-device gate was paradoxical: the deployed Fully Kiosk WebView was the first place a kids' view change could be judged, so judging it required shipping it. Two things fixed that. First, the tablet's CSS viewport is knowable — the Lenovo IdeaTab's 2560 × 1600 panel is 1280 × 800 CSS px at 2× DPR — so a desktop browser window at that size is a faithful layout check for everything except what only Android can answer (font coverage, large box-shadow rendering, touch, sleep/wake). Second, staging a kiosk state by hand (wipe today's completions, stamp a few rows, override a config key) was the real cost of looking locally, so it became code: ~BearCub.Dev.Scenarios~, compiled in dev and test only, one named function per reviewable state, run inside the server VM so overrides and broadcasts take effect live. The Android-only questions get designed out where possible — the early bird's sparrow shipped first as a hieroglyph text glyph (U+1316A), which Safari and Chrome drew at different sizes and Android would not have drawn at all; it became an inline SVG path extracted from the OFL Noto font with fontTools, identical everywhere. What is left for the tablet is a short post-deploy checklist, not a gate. A delivered PRD's gate wording does not bind ops process; the human ruled that explicitly.

Revised [2026-10-07 Wed]: the post-deploy checklist is optional, not owed. Three gates after this entry (good-standing, routine-schedule, night-owl-bonus) each wrote tablet items as "still to run" and no record shows any was run; the one that went to the backlog sat open a month. The human ruled at the night-owl-bonus Batch 1 retro that the gate is localhost QA, full stop, and that Android-only questions are designed out rather than checked later. CLAUDE.md's gate-close convention carries the ruling.

* [2026-07-12 Sun] A pinned ~nil~ in an Ecto query comparison raises, it doesn't match
Comparing a field against a pinned ~nil~ (~c.routine == ^value~, where ~value~
is ~nil~) raises ~ArgumentError~ at query time rather than silently matching
~nil~ rows — Ecto only treats literal, unpinned ~nil~ as an ~IS NULL~ rewrite,
never a pinned variable that happens to hold ~nil~. Any query bucketing rows
by a nullable discriminator needs a dedicated ~is_nil/1~ clause for the ~nil~
bucket; the pin-and-compare form that works for every other bucket value
silently doesn't generalize to it. Bit twice in the same initiative on
latent, pre-existing code exposed the moment a nullable column arrived:
~next_position/2~ (Story 02) and the ~neighbor/2~ helper behind ~move_chore/2~
(Story 03) — both had compared against a bucket value that was always
non-nil until extras introduced ~routine = nil~ as a real bucket. Evidence:
the two withdrawn repair-class advisories in
docs/2026-07-11-extras/DESIGN.org's git history (§Data Model, ~next_position/2~
and ~move_chore/2~'s neighbor lookup) and both stories' PLAN.org LOGBOOK
entries.

* [2026-07-12 Sun] Confirmed pattern: give a new entity an existing entity's satellite machinery via a nullable discriminator, not a parallel table
When a new entity needs everything an existing entity already has —
completions, undo, history, PubSub, admin toggles — extending the existing
table with a nullable discriminator column beats adding a parallel table with
its own copy of that machinery. The Extras initiative's D27
(docs/2026-07-11-extras/DESIGN.org) modeled an extra as a ~chores~ row with
~routine = nil~, reusing the ~completions~ table's FK, partial-unique-per-day
index, undo, on-behalf marking, and history verbatim; the entire schema cost
was one nullability migration plus the ~is_nil/1~ query-clause discipline
above. Rejected alternatives (D27): a separate ~extras~ table (forfeits
completion reuse, forcing a duplicate ~extra_completions~ table or a
polymorphic FK on SQLite/Ecto) and a third routine constant ~:extra~ (a
category error dragging windowless, reset-free extras through window logic
built for routines). Held across all six of that initiative's stories with
zero new state machinery introduced.

* [2026-07-12 Sun] Ecto/SQLite migrations: a disabled DDL transaction needs a pinned connection too
With ~@disable_ddl_transaction true~, ~Ecto.Migration.Runner~ dispatches each
~execute~/~create table~/~drop table~ call through a separate Agent process,
not the migration module's own process. On a pooled (non-Sandbox) SQLite
connection this means consecutive statements can land on different physical
connections; a later statement (e.g. recreating an index right after a
rename) can then observe a stale, pre-drop schema and fail with a spurious
"already exists" error. This bites any migration that must run outside a
transaction at all — most commonly a ~PRAGMA~ toggle (~foreign_keys~, needed
before a table rebuild that would otherwise reject or cascade-delete through
the drop) that SQLite makes a silent no-op inside a transaction. Fix: pin the
whole migration body to one physical connection by issuing raw
~Ecto.Adapters.SQL.query!/3~ calls inside ~repo().checkout/1~, bypassing the
Runner's execute/create/drop macros entirely — wrapping the macros themselves
in ~repo().checkout(fn -> ... end)~ does *not* help, since checkout pins the
calling process, not the Agent process the macros actually dispatch to.
Reproduced directly on both an isolated multi-connection test repo and the
real ~mix ecto.migrate~ path (pool_size 2 default); see
~priv/repo/migrations/20260712180527_relax_chores_routine_nullability.exs~
and its migration test for the working pattern. Adjacent fact: ~ecto_sqlite3~
(0.24.1) has no working column-modify — any SQLite constraint change is
always the create-new/copy-rows/drop-old/rename table rebuild, never an
in-place ~ALTER COLUMN~.

* [2026-07-10 Fri] Nix deploy: a deps change surfaces late inside nixos-rebuild (hash bump, deps_nix layout)
The mix deps fetch in ~nix/package.nix~ is a fixed-output derivation:
when ~mix.lock~ changes but the pinned ~hash~ does not, Nix silently
reuses the *cached pre-change deps* and the failure surfaces late — as
=Could not find application :<new dep>= during ~mix release~ inside
~nixos-rebuild~, not at fetch time.

Fast TOFU loop that avoids committing broken pins: on the target box,
~nix-build~ a one-off expression that calls
~beamPackages.fetchMixDeps~ with ~builtins.fetchGit~ of the
already-pushed rev and ~hash = lib.fakeHash~; the mismatch error
prints the real hash (no sudo needed). Bonus: the deps land in the
store, so the subsequent ~nixos-rebuild switch~ skips refetching.

Second variant [2026-10-07 Wed]: a dependency bump that regenerates ~nix/deps.nix~ under a newer deps_nix can change derivation layout, not only hashes. deps_nix 3.1 wrapped heroicons in a derivation exposing the checkout at =$out/src= where ~package.nix~ still linked the derivation root as =deps/heroicons=, so ~assets.deploy~ could not find =optimized/24/outline= and the release failed, again inside ~nixos-rebuild~, eight hours and a whole batch after the bump landed (b2c7dc4 bumped at 10:08, 398b013 fixed it twelve minutes after the batch's gate). ~mix precommit~ cannot see ~nix/~, so the batch ran green all day on a broken deploy. Rule: a commit that regenerates ~nix/deps.nix~ is verified by a build on the target box before feature work stacks on it, either deployed on its own or through the ~nix-build~ loop above run against the real ~package.nix~, so a layout change fails on the bump and not on the feature.

* [2026-07-10 Fri] Elixir: map-pattern keys must be literals or pins
~assert %{chore.id => found} = ...~ is not legal Elixir — a pattern
key can't be an arbitrary expression. Bind first, then pin:
~chore_id = chore.id; assert %{^chore_id => found} = ...~.
Wider point: code blocks embedded in planning docs are never
compiler-checked, so expect (and review for) this class of fix when
implementing from written plans.

* [2026-07-10 Fri] Nix: asset-binary versions drift from the mix config pins
Under the sandboxed build, =MIX_TAILWIND_PATH= / =MIX_ESBUILD_PATH=
supply nixpkgs binaries, which drift ahead of the versions pinned in
~config.exs~ (seen: esbuild 0.27.2 vs configured 0.25.4 → a warning in
the build log). The config pin only governs mix-managed downloads on
dev machines; the warning is cosmetic in the Nix build, but align the
pin when convenient so real incompatibilities aren't masked by a
warning everyone has learned to ignore.

* [2026-07-10 Fri] tzdata boots fine from the read-only Nix store
With ~config :tzdata, :autoupdate, :disabled~, tzdata reads its
bundled tables from its priv dir in the store without complaint — no
~:data_dir~ override needed. (If autoupdate is ever re-enabled it
*will* need a writable ~data_dir~, e.g. the service's
StateDirectory.) tzdata also drags in hackney + friends as transitive
deps; they're never started and Req remains the app's HTTP client.

* [2026-07-17 Fri] Tests must pin the local datetime, never inherit the real clock
(Revises the 2026-07-10 entry this replaces, which undersold the actual
risk as a single-second edge race.) LiveView tests deliberately compute
expected routine state from the real clock with the app's own pure
functions — no clock mocking — but "no mocking" is not the same as "no
pinning." 15 tests across ~KioskLiveTest~, ~Admin.TodayLiveTest~, and
~Admin.ChoreLiveTest~ called ~auto_routine()~/~active_routine()~ without
pinning ~:routine_windows~, so they inherited whichever routine (or the
23:00–05:00 Good Night gap) the real wall clock happened to land in —
not a theoretical instant-edge race, but a deterministic failure for the
*entire* six-hour gap, ridden across two initiative stories'
close-outs (docs/2026-07-15-gamification-points/stories/story-06-kiosk-failed-marking.org,
story-07-collapse-delay.org, both confirmed via a ~git stash~ baseline
at the same wall-clock time) before being repaired in commit =4fc7247=.
Fix, now a mechanism rather than a habit: routine timings live in
~schedule_versions~ (D120), so a test pins them by inserting a version,
and ~BearCubWeb.ConnCase~'s shared setup does it by default
(~BearCub.ScheduleHelpers.pin_default_schedule/0~: morning open all day,
evening never, identical on all seven weekdays). A test that needs the
migration's real windows opts out with ~@tag :real_schedule~; one that
needs the evening or a gap calls ~evening_active/0~ or
~put_windows/2~ from the same module. This still calls the real clock
(~LocalTime.now()~, never mocked); it only fixes which window that real
clock falls into. A genuine instant-of-the-edge race (helper evaluates a
hair before 05:00/17:00/23:00, mount lands a hair after) remains
theoretically possible — if that ever actually fires, rerun; still don't
reach for clock mocking. Two SQLite traps in the pin: ~effective_at~ is
unique to the second, so helpers stamp one second after the latest
version and the pin sits an hour back; and the pin's insert must be the
test transaction's first statement, because a read-then-write upgrade
fails at once with "Database busy" while another connection holds the
write lock (async modules skip the pin for the same reason).

The pin fixes the /window/, nothing else the clock decides. A test that stages a tap relative to the real clock (~DateTime.add(LocalTime.now(), -10 * 60)~) still inherits two things from the hour it runs: the local /date/ (just after midnight, ten minutes back is yesterday, so today's routine-day never completes), and the early bird /verdict/ (before the 07:45 cutoff, an earn is early and a badge reads +R+E). Two routine-schedule kiosk tests rode both through Story 04's close-out and failed only at the 00:06 gate run (fixed in =dc94516=). Clock-relative instants stay inside today, and a test asserting a plain +R pins the cutoff with ~put_cutoff(~T[00:00:00])~.

* [2026-07-10 Fri] Ops: reach the server over Tailscale, not the LAN IP
From the dev machine the box's LAN IP times out on ssh; the Tailscale
machine name (~nixos~) connects. Non-sudo deploy steps (~git pull~,
one-off ~nix-build~) are scriptable over ssh; ~nixos-rebuild switch~
still needs a real terminal for sudo.
