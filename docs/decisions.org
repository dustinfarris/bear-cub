* D57 (2026-07-25) — Rewards live in a new ~BearCub.Rewards~ context; ~BearCub.Points~ composes earnings and spends; ~Chores.points_total/2~ becomes ~Chores.earnings/2~ (raw signed)
:PROPERTIES:
:CUSTOM_ID: d57
:END:

Redemption gets two new modules rather than an extension of ~Chores~. ~BearCub.Rewards~ owns the ~rewards~ / ~redemptions~ tables, every write path, the availability derivation, and its own PubSub topic, and knows nothing about chores or completions. ~BearCub.Points~ is a composition module — the only place in the app that knows both sides — exposing ~balance/2~ (raw signed), ~total/2~ (the D41 floored display figure), and their whole-render map forms. ~Chores.points_total/2~ is renamed ~Chores.earnings/2~ and returns the raw signed earnings unfloored; the floor moves up to ~Points~, where the complete summation lives, and ~Chores~ never learns ~Rewards~ exists. Rejected — putting ~redemptions~ inside ~BearCub.Chores~: a naming lie (a redemption is not a chore), and ~chores.ex~ already carries kids, chores, extras, completions, fails, and the points derivation in ~450 lines. Rejected — letting the points derivation read the ~redemptions~ table directly from ~Chores~: inverts the dependency direction the repo already treats as an invariant for ~Chores~ → ~Calendars~; the moment ~Chores~ imports ~Rewards~, a rewards failure can reach the chore path. Rejected — threading the spend in as an argument (~points_total(kid, date, other_signed_inputs \\ 0)~): keeps the contexts clean but pushes the summation into every LiveView, so a missed caller is a silently wrong balance. Settles rewards/SC-3 and rewards/SC-4 placement. → rewards/Key Behaviors (contexts and dependency direction), rewards/Overview.

* D58 (2026-07-25) — ~rewards~ carries a nullable ~kid_id~ (audience) and a ~repeatable~ boolean (frequency) as orthogonal knobs
:PROPERTIES:
:CUSTOM_ID: d58
:END:

A reward's ~kid_id~ is nullable — NULL means offered to any kid, set means offered to that kid only — and is a *purely administrative audience control*, answering "is this on offer to both kids, or just one?" and nothing more. Repeatability is a separate boolean: repeatable means available again the next local day, one-time means claimable once. The two are never coupled, so a one-time reward offered to both kids ("your own bike" — each may earn one) and a repeatable kid-scoped reward ("an extra bedtime story") are both legal. ~kid_id~ is set programmatically from the form's kid selection, never cast from attrs, matching ~create_chore/2~. This is the nullable-discriminator pattern (D27; ~docs/learnings.org~ [2026-07-12]) applied a third time. Rejected — a family-wide-only catalog: cannot express "the ATM toy is this child's to earn". Rejected — a per-kid-only catalog mirroring ~chores~: forces duplicate rows for every shared reward, and the duplicates then drift in price. Rejected — coupling the knobs (e.g. "one-time implies kid-scoped"): would forbid two legitimate combinations for no gain. Rejected — a ~cooldown_days~ integer (0 same-day, 1 next-day, NULL one-time): strictly more general and would collapse both concepts into one field, but nothing in family use asks for a 3- or 7-day cooldown; ~repeatable~ widens to it additively if it ever arrives. Settles rewards/SC-1, rewards/SC-5 storage. → rewards/Data Model.

* D59 (2026-07-25) — One ~redemptions~ table; state derived from nullable timestamp markers, never a status column
:PROPERTIES:
:CUSTOM_ID: d59
:END:

The request and the spend are one row. ~requested_at~ / ~approved_at~ / ~declined_at~ / ~reversed_at~ are nullable markers, and every state is a query over them: pending, lapsed (requested, unanswered, dated before today), approved, reversed, declined. Contribution is marker-first, mirroring ~extra_contribution/2~'s ~cond~ — reversed → 0, approved → −points, otherwise → 0 — so a reversed row is retained forever as the trail. This is D10's posture and the ~undone_at~ / ~failed_at~ precedent: the row records what happened and when. Rejected — a ~status~ string or ~Ecto.Enum~ column: more legible at a glance, but it stores a value the markers already determine, and any store-plus-derive pair eventually drifts; the timestamps carry strictly more information (they answer *when*). Rejected — a separate ~redemption_requests~ table with the spend as a second table: two tables to express one lifecycle, a join for every history read, and a forked audit trail — the same argument D39 used to reject a ~points_ledger~. Settles rewards/SC-6 verdict states, rewards/SC-7 permanence. → rewards/Data Model, rewards/Key Behaviors (availability).

* D60 (2026-07-25) — The redemption price is snapshotted on the row; the reward name is not
:PROPERTIES:
:CUSTOM_ID: d60
:END:

~redemptions.points~ is a price snapshot taken at row creation — at *request* time for the kid leg (that is the deal the child was shown) and at redeem time for the parent-direct leg. The total is cumulative all-time and purely derived, so reading a live ~rewards.points~ at derivation time would make history mutable: a parent raising a price would retroactively deepen every past spend of it and silently move a child's balance, potentially into debt after the fact. A ~reward_name~ snapshot is deliberately *not* taken — reward rows are archived, never deleted ([[#d68][D68]]), so the join is always available and the name stays a single source of truth; a rename is correctly reflected in history, because a parent renaming a reward is clarifying what it is, not creating a different one. Rejected — snapshotting the price at approval instead of request: lets a price change between ask and answer alter the deal after the child committed to it. Rejected — no snapshot, joining to ~rewards~ for the price: makes a derived cumulative total unstable under ordinary admin edits. Settles rewards/SC-7. → rewards/Data Model.

* D61 (2026-07-25) — One open request per kid per local day, enforced by a partial unique index; lapse is derived and free
:PROPERTIES:
:CUSTOM_ID: d61
:END:

A partial unique index on ~redemptions (kid_id, local_date) WHERE requested_at IS NOT NULL AND approved_at IS NULL AND declined_at IS NULL~ caps a child at one open ask per day — the same technique the shipped ~completions (chore_id, local_date) WHERE undone_at IS NULL~ index already uses. Including ~local_date~ in the key is what makes lapse free: yesterday's unanswered request cannot block today's, with no job and no cleanup, so an unanswered ask simply does not carry over. A racing duplicate hits the index and returns ~{:error, changeset}~, which callers treat as already-asked — the posture ~complete_chore/3~ takes on a racing double-tap. The index has no reward component, so it constrains how many asks a kid has open, never which reward they may ask for: repeatability, kid scoping, and the open-request cap are three independent constraints. Rejected — a scheduled cleanup or expiry job for stale requests: midnight machinery the derived-state doctrine (D10) forbids, buying nothing the dated key does not already give. Settles rewards/SC-6 (an unanswered request does not carry over). → rewards/Data Model (indexes), rewards/Screens (admin approval queue).

* D62 (2026-07-25) — Availability is fully derived, and both predicates are scoped per-kid
:PROPERTIES:
:CUSTOM_ID: d62
:END:

Nothing about availability is stored and no job runs. Over the unreversed approvals for a given reward *and a given kid*: one-time is consumed if any such row exists on any day; repeatable is on cooldown if such a row exists dated today. "One-time" therefore means each kid may claim it once ever, "repeatable" means each kid may claim it once per day, and the next local day arriving is what restores a repeatable reward — the same D10 mechanism by which a completed chore becomes incomplete at midnight. A reversal restores availability for free, since both predicates exclude reversed rows. Pending requests do not consume (no ~approved_at~), so there is no cross-kid race; the surviving same-kid interleaving — ask on the kiosk, parent direct-redeems the same reward for the same child, then approves the open request — is what the approval-time re-check ([[#d63][D63]]) exists to catch. Rejected — global (family-wide) one-time consumption: it reads ~repeatable = false~ as physical scarcity, one object gone the moment anyone takes it, which inverts what ~kid_id~ is for ([[#d58][D58]]) — a parent wanting "each of you can earn one of these" would be pushed into duplicating the reward per kid, exactly the duplicate-and-drift problem the nullable ~kid_id~ exists to prevent, and it would let a card change state in one child's column because of something that happened in the other's. Rejected — a global repeatable cooldown: a family reward taken by one kid would sit dimmed in the sibling's column all day with no legible reason. Rejected — guarding availability at request time with a reserve model: rejected on its own merits under [[#d63][D63]]. Family-scarce rewards (one object claimable once across the whole family) are a distinct concept, deliberately deferred and not to be reintroduced by reading scarcity into ~kid_id~. Settles rewards/SC-5. → rewards/Key Behaviors (availability), rewards/Screens (kiosk card states), rewards/Out of Scope.

* D63 (2026-07-25) — Affordability is strict on both legs against the raw signed balance; no override, no reserve
:PROPERTIES:
:CUSTOM_ID: d63
:END:

One rule, one function, both legs: ~Points.balance(kid, today) >= reward.points~, evaluated against the *true signed sum* and never the floored display figure — which D41 pre-authorizes in as many words. A parent's direct-redeem is bound by exactly the same check as a child's request; there is no override and no IOU. It is checked twice: at request time on the kiosk, where an unaffordable reward renders visibly locked and is not tappable (a rendering rule before it is a validation), and at approval time in admin, where affordability *and* availability are re-validated because both the balance and the catalog move between ask and answer; a failed re-check tells the parent which check failed rather than silently no-opping. Rejected — a parent override redeeming into visible debt (a D49-shape escape hatch): D49's override is legitimate because it nets a penalty in the child's favor against a boundary the child could not cross alone; an affordability override runs the opposite way — it manufactures debt the child never agreed to, on a surface (D41/D43) that structurally cannot display a negative number. Rejected — checking against the floored total ~max(0, balance)~: forgives real debt at spend time and contradicts D41's explicit instruction that a balance-needing feature sums the raw signed rows. Rejected — a reserve/hold model escrowing a pending request's price: creates two balances (true and available) that the always-visible badge (D43) cannot show at once, so the badge would either drop when nothing has been earned or spent, or disagree with what the child can actually afford; the race it would close is closed instead by the approval-time re-check plus the one-open-request index ([[#d61][D61]]) at zero display cost. Settles rewards/SC-4. → rewards/Key Behaviors (affordability), rewards/Screens (kiosk card states, admin).

* D64 (2026-07-25) — Redemption widens hidden debt: the kiosk keeps the floor and explains with a lock glyph; every admin balance shows the true signed figure
:PROPERTIES:
:CUSTOM_ID: d64
:END:

A child at true balance 2 who then takes a fail sits at true −3 while the badge honestly shows 0. Redemption does not create this — D41 accepted it explicitly ("two kids both showing 0 may have different true standings") — but it *widens* it, because a spend is now a routine way to arrive near the floor, so the trade-off is re-ruled here rather than silently inherited. No spend-time guard can close it: affordability ([[#d63][D63]]) already guarantees a spend never drives the balance below zero, so all residual debt comes from fails *after* a spend, by construction outside any spend-time check. The resolution is not to hide less on the kiosk but to hide nothing in admin. The kiosk keeps the floor (D41, D43) and the *lock glyph on an unaffordable card is the pre-reader-legible explanation* — a child who cannot read a negative number can read a lock, and needs no number to act correctly. Admin displays the true signed balance, negative included, wherever it shows one (approval queue, direct-redeem picker, history), because the parent is a reader and the only party who can act on debt. Rejected — surfacing the true negative on the kiosk: contradicts D41/D43's floor and shows a pre-reader a number they cannot act on. Rejected — floored balances in admin for consistency with the kiosk: hides the only signal the party who can act on it needs. Settles rewards/SC-3, rewards/SC-4, rewards/SC-6. → rewards/Key Behaviors (hidden debt), rewards/Screens (kiosk card states, balances in admin).

* D66 (2026-07-25) — Reward cards resolve in one seven-row precedence table, with one dim treatment and three glyphs
:PROPERTIES:
:CUSTOM_ID: d66
:END:

Verdict states and availability states are the same kind of thing — derived from redemption markers plus ~local_date == today~ — so they resolve in one ordered table, first match wins: retired → absent; one-time consumed on an earlier day → absent; pending today → =⏳=; declined today → dim + declined glyph; claimed today → dim + check glyph; unaffordable → dim + lock glyph; otherwise a full-color, tappable card. Claimed outranks unaffordable because after a spend the balance is usually below the price again and "you got this today" is strictly more informative. The three dim states share one layout and differ only by glyph, so a pre-reader learns three glyphs against one layout rather than three layouts, and the pending =⏳= is the same glyph the banner button already carries. The declined row doubles as the *re-ask block*: a declined row does not occupy the one-open-request index slot ([[#d61][D61]]), so without this rendering rule a child could re-tap and re-queue indefinitely — deriving "declined for this reward today" and rendering it untappable closes the loop with no new storage (the D55 day-scope pattern). The reward card surface, the dim+glyph vocabulary, and the =🎁= / =⏳= button are new kids'-view indicators and are *pending design-language recordings*, written into ~docs/design-language.org~ by the story that lands them per the D48 / D54 pattern — the existing "do not add further indicators without a ruling" clause makes this mandatory. Rejected — hiding a consumed one-time reward immediately on approval: a child who saved 500 for the ATM toy would watch it vanish the instant it was granted, which reads as a bug rather than a triumph; it shows as claimed for the rest of the local day, then disappears. Rejected — showing consumed rewards as claimed permanently: dead cards accumulate forever in a catalog a pre-reader scans by glance. Rejected — hiding repeatable rewards while on cooldown: the catalog would change shape day to day with no visible reason. Settles rewards/SC-6. → rewards/Screens (kiosk card states, design-language recordings).

* D72 (2026-07-25) — The points aggregate rewrite is claimed and lands early, as a pure performance refactor; roster drift is surfaced, not fixed
:PROPERTIES:
:CUSTOM_ID: d72
:END:

The deferred ~points_total/2~ N+1 rewrite is claimed as a batch member of this initiative and lands *before* affordability depends on it. The shipped derivation issues one query per distinct ~(routine, local_date)~ pair plus two per pair — roughly 1,460 queries per kid per render after a year — and runs on every broadcast on every connected surface; redemption makes it load-bearing three ways (the affordability check on every tap and every card render, the badge, and every admin balance display). The target is ~Points.balances(local_date) :: %{kid_id => signed_integer}~ in three grouped queries — extras, routine-days, redemptions — O(1) queries for a whole render, with ~Points.balance/2~ delegating to the map and ~Points.total~ / ~Points.totals~ applying the D41 floor on top. No memoization, no cached totals, no materialized column: the derived-state doctrine (D10) is not negotiable and the aggregate is fast enough that caching would buy nothing. Semantics stay *unchanged*: the claimed item is the query shape, not the derivation's meaning. This preserves a discovered defect — ~routine_day_contribution/3~ evaluates historical routine-days against the kid's *current* roster, so adding a morning chore today retroactively wipes past ~+R~ and deleting one can grant points never earned; redemption raises the stakes, since a roster edit can move a balance after a spend, potentially into debt with no fail involved. Roster drift is captured as its own backlog entry at initiative close: a fix needs its own ruling, and a ~chores.inserted_at~-bounded roster would handle additions but not deletions, so the honest fix is not obviously cheap. The pinning tests must include a roster-drift case — a routine-day evaluated after the roster changed — so behavior preservation is proven on the weird path; a refactor that silently "fixed" drift would be an unruled semantic change smuggled in under a performance story. Rejected — fixing drift inside the rewrite: a semantic change disguised as a refactor, and unruled. Rejected — deferring the rewrite to a later initiative: rewards/SC-9 requires the affordability check be cheap on every tap and stay cheap as months accumulate, which the shipped shape does not satisfy. Settles rewards/SC-9. → rewards/Key Behaviors (points aggregate rewrite, testing), rewards/Out of Scope.

* D73 (2026-07-25) — Lapse is terminal at the write layer: ~approve_redemption/3~ and ~decline_redemption/2~ refuse a lapsed row, not only a verdict-stamped one
:PROPERTIES:
:CUSTOM_ID: d73

:PROPERTIES:
:CUSTOM_ID: d87

Geometry is now identical in every browser and needs no font — which closes D102's provisional clause without an on-device check, and is the pattern for any future glyph outside the emoji set: inline SVG, never text relying on font coverage. The look is unchanged from what the human chose. Rejected — bundling a one-glyph font subset: a webfont adds a request and a ~@font-face~ to solve a problem one path element solves. Rejected — tuning per-browser margins around the text glyph: it would still be tofu on the only render target that matters. Settles nothing new against any PRD. → design-language Rulings.

* D104 (2026-09-06) — The early bird is one combined badge on a bigger sun plus an EARLY pill, no bird — supersedes the visual of D101, D102 and D103
:PROPERTIES:
:CUSTOM_ID: d104
:END:

Human ruling from a mockup reviewed at 1280 × 800 through the new local gate. The bird — emoji ([[#d101][D101]]), hieroglyph ([[#d102][D102]]), inline SVG ([[#d103][D103]]) — is gone. The sun's bonus badge carries ~R + E~ as one number on an early morning (=+7= at defaults) and plain ~R~ otherwise, and a white pill reading =EARLY= in the kid's own banner color sits under the sun, centered, overlapping its lower rays. Both are one signal: the badge is hidden when the routine-day is failed as before ([[#d47][D47]]), and ~early_bird?~ is already false when failed, so a fail drops the extra points and the pill together. The completion icon grows from ~size-11~ to ~size-14~, sun and moon alike so the two routines stay one shape, and the badge steps up from ~text-xs~ to ~text-sm~ to match; offsets (~-right-4 -top-1~ badge, ~-bottom-1.5~ pill) keep both inside the ~py-5~ banner so nothing overhangs the standing band beneath. This reverses D101's rejection of a folded number on the reasoning that a kid should see *why* the number moved: the pill is the why, in a word rather than a glyph, and it is the first text on the kids' banner — accepted knowingly; a pre-reader gets the bigger number and the extra white shape, a reader gets the word. Rejected — keeping a glyph beside the pill: two indicators for one fact, and the human's mockup had none. Rejected — the pill in ~bg-success~ like the badge: it would read as a second badge; white on the kid color reads as a label. D103's rule for future non-emoji glyphs (inline SVG, never font-dependent text) stands even though its sparrow does not. Settles the early-bird item's visual, third and final form today. → design-language Rulings.
