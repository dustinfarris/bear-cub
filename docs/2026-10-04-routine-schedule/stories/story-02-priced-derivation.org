Excerpt (verbatim):

#+begin_quote
  ** ~routine_day_status/3~ gains ~first_failed_at~

No column changes on ~completions~. The per-routine-day status map gains a fifth key, ~first_failed_at~ — the earliest ~failed_at~ among that routine-day's completions, ~nil~ when never failed — selected as ~MIN(failed_at)~ in the same aggregate that already yields ~last_completed_at~ ([[file:../decisions.org::#d122][D122]]). ~Chores.standing/2~ ignores the new key.

  ** Pricing: each term at the instant it came into being (SC-1, SC-4)

A versions table keyed by /date/ fails SC-1 on a same-day edit: a morning earned at 07:30 under ~R = 5~ would re-score when ~R~ is raised at 10:00 that day; making the edit wait until tomorrow fails SC-3. So versions carry an instant, and each term resolves against the version in force at /its/ instant ([[file:../decisions.org::#d121][D121]]):

| term | instant it is priced at                                             | what is read from that version                                |
|------+---------------------------------------------------------------------+---------------------------------------------------------------|
| ~+R~ | ~last_completed_at~ — the last live tap on the day's roster         | ~routine_bonus~                                               |
| ~+E~ | ~last_completed_at~ (same instant as ~+R~)                          | the cutoff for ~local_date~'s weekday, and ~early_bird_bonus~ |
| ~−R~ | ~first_failed_at~ — the earliest ~failed_at~ that routine-day       | ~routine_bonus~                                               |

The weekday is always that of the routine-day's ~local_date~. "Early" and "how much" for the early bird come from the same version, so the verdict and the amount are judged by the same rules.

Consequences:

- An earned day failed after ~R~ changed, then redone: the redo is a new last live tap, so ~+R~ re-prices at the new value and the fail costs the new value — net 0, as today.
- An earned day failed after ~R~ changed and /not/ redone: the day is no longer complete, so ~+R~ drops out and the day nets ~−R~ at the new value — the same shape as today, at the price in force when the fail happened.
- An undo-and-redo after an edit re-earns at the new ~R~ (and is re-judged against the new cutoff). The kid's total moves by the difference at the moment of the re-tap; nothing they already held moved.
- ~last_completed_at~ is "the last live tap on the day's roster", which is /usually/ the moment the day became earned but not always. Under [[file:../decisions.org::#d81][D81]] archiving a chore drops it from that day's roster: if it held the last tap, ~last_completed_at~ falls back to an earlier tap and ~+R~ / ~+E~ re-price against the version in force then; an archive that completes the roster with no new tap is priced at the existing last tap. Accepted: the trigger is an archive, not a schedule edit, and D81 already lets an archive change that day's result, so SC-1 (which is about schedule changes) is not engaged.

  ** SQL gathers facts; Elixir prices them in one place

~contribution/4~ becomes ~contribution(versions, routine, local_date, facts)~ and is still the single place routine-day facts become points, called by both derivation routes ([[file:../decisions.org::#d122][D122]]):

#+begin_src elixir
# +R if earned, -R if failed, +E if early — each resolved against
# the version in force at its own instant (D121).
defp contribution(versions, routine, local_date, facts) do
  earn = facts.last_completed_at && Routines.in_force(versions, facts.last_completed_at)
  fail = facts.first_failed_at && Routines.in_force(versions, facts.first_failed_at)
  early? = early_bird?(routine, facts.earned?, facts.failed?, facts.last_completed_at,
                       earn && Routines.day(earn, local_date))

  if(facts.earned?, do: earn.routine_bonus, else: 0) +
    if(facts.failed?, do: -fail.routine_bonus, else: 0) +
    if(early?, do: earn.early_bird_bonus, else: 0)
end
#+end_src

(Illustrative shape, not a signature contract: the constraint is one function, both routes, each term at its own instant.)

~earnings/2~ and ~earnings_by_kid/1~ each call ~Schedules.versions/0~ once and pass the list down. Public per-routine-day functions (~routine_day_contribution/3~, the kiosk pricing helper) take the version list as an argument (with a convenience arity that fetches it), so a whole render loads the history once rather than per call. [[file:../decisions.org::#d72][D72]]'s "two queries regardless of history" becomes three, still O(1); the versions table grows by one row per parent save.
#+end_quote

* User Story

As a kid, I need the points I earned on a routine to stay exactly what they were when I earned them, so that my total and my shop balance don't move when a parent changes the rules.

* Technical Notes

- The Design excerpt above is the source of truth for this story; [[file:../DESIGN.org][DESIGN.org]] is broader context only.
- This story depends on Story 01, because pricing reads ~Schedules.versions/0~ and resolves through ~Routines.in_force/2~ and ~Routines.day/2~.
- Scope is the derivation in ~BearCub.Chores~: ~routine_day_status/3~'s aggregate, ~contribution~, ~early_bird?~ (public ~early_bird?/2~ and the private clauses around ~lib/bear_cub/chores.ex:533–561~), ~routine_day_contribution/3~, ~earnings/2~ and ~earnings_by_kid/1~. After this story ~Chores~ reads no ~Routines.bonus/0~, ~early_bird_cutoff/0~ or ~early_bird_bonus/0~. The functions themselves stay until Story 04, because ~kiosk_components.ex~ still calls ~Routines.bonus/0~ for display. Version 0 and config agree, so the kiosk's figures stay correct in between.
- The kiosk pricing helper (~routine_day_pricing/3~) belongs to Story 04, where the kiosk consumes it. Shape ~contribution~ so that Story 04 can build it from the same internals without a second pricing path.
- *Convert the domain tests' config pins in this story.* ~test/bear_cub/chores_test.exs~, ~points_test.exs~, ~rewards_test.exs~ and ~points_redemptions_test.exs~ pin ~:routine_bonus~, ~:early_bird_cutoff~ and ~:early_bird_bonus~ with ~Application.put_env~. Once ~Chores~ stops reading config those pins silently do nothing, and a test asserting a non-default value either fails or, worse, passes for the wrong reason. Each becomes a version insert at a fixed instant before the fixture's completions. Grep for ~put_env~ in those files and leave no routine-bonus or cutoff pin behind.
- The agreement test is the one with teeth (excerpt). Carry forward the effort-multiplier Story 02 near-miss recorded in its PLAN LOGBOOK: a fixture whose terms cancel proves nothing. Assert each route against a hand-derived figure, and confirm that figure differs from what pricing against the current version alone would give. Otherwise a route resolving every term at "now" passes.
