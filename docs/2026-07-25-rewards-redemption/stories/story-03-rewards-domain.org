* Design

Verbatim from DESIGN.org for this story's scope.

** Data Model

Two new tables. ~completions~ and ~chores~ are untouched.

*** ~rewards~

| column       | type                 | notes                                                                              |
|--------------+----------------------+------------------------------------------------------------------------------------|
| ~kid_id~     | FK, *nullable*       | NULL = offered to any kid; set = offered to that kid only. Audience, never scarcity |
| ~name~       | string, NOT NULL     |                                                                                    |
| ~icon~       | string, NOT NULL     | emoji, per the chore-icon convention; form default =🎁=                             |
| ~points~     | integer, NOT NULL    | the price                                                                          |
| ~repeatable~ | boolean, NOT NULL    | default ~true~                                                                     |
| ~position~   | integer, NOT NULL    | parent-controlled order                                                            |
| ~retired_at~ | ~utc_datetime~, NULL | soft archive                                                                       |

~kid_id~ is set programmatically from the form's kid selection and never cast from attrs, matching the shipped ~create_chore/2~ treatment.

Why *nullable ~kid_id~* rather than a family-only or per-kid-only catalog: the nullable discriminator is the repo's confirmed pattern (D27; ~docs/learnings.org~ [2026-07-12]). One column buys both models, and the two knobs stay orthogonal — "who is this offered to" (~kid_id~) is a separate question from "how often may a kid claim it" (~repeatable~). ~list_rewards(kid, local_date)~ is ~where is_nil(kid_id) or kid_id == ^kid.id~, not retired, ordered by ~position~.

~kid_id~ is *purely an administrative audience control*: when a parent creates a reward they are answering "is this on offer to both kids, or just one?" — nothing more. It says nothing about how many times the reward can be claimed; that is ~repeatable~'s job, and both questions are answered per-kid (Key Behaviors → availability).

A one-time reward offered to *both* kids ("your own bike" — each of them may earn one) and a repeatable kid-scoped reward ("an extra bedtime story for Ollie") are both legal and both meaningful; the two knobs are never coupled.

~repeatable~ is *a boolean, not a cooldown interval*. Repeatable means available again the next local day — a fixed one-day cooldown. A ~cooldown_days~ integer would be strictly more general and would collapse both concepts into one field, but nothing in family use asks for a 3-day or 7-day cooldown; if it ever arrives, ~repeatable~ widens to ~cooldown_days~ additively.

*** ~redemptions~ — the D42 signed input

| column         | type                 | notes                                                 |
|----------------+----------------------+---------------------------------------------------------|
| ~kid_id~       | FK, NOT NULL         | set programmatically, never cast                      |
| ~reward_id~    | FK, NOT NULL         |                                                       |
| ~points~       | integer, NOT NULL    | *price snapshot* taken at row creation                |
| ~local_date~   | date, NOT NULL       | the local day the row was created                     |
| ~requested_at~ | ~utc_datetime~, NULL | NULL = parent direct-redeem (no kid request)          |
| ~approved_at~  | ~utc_datetime~, NULL |                                                       |
| ~declined_at~  | ~utc_datetime~, NULL |                                                       |
| ~reversed_at~  | ~utc_datetime~, NULL | the reversal marker                                   |
| ~source~       | string, NOT NULL     | ="kiosk"= / ="admin"=, mirroring ~completions.source~  |

Contribution is marker-first, mirroring the shipped ~extra_contribution/2~ ~cond~ exactly:

#+begin_src
reversed_at set  ->  0        (reversed; row retained forever as the trail)
approved_at set  -> −points   (the spend)
otherwise        ->  0        (pending, declined, or lapsed)
#+end_src

State is derived from nullable timestamp markers, *never a status column* — D10's posture and the ~undone_at~ / ~failed_at~ precedent:

#+begin_src
pending?   = requested_at && !approved_at && !declined_at && local_date == today
lapsed?    = requested_at && !approved_at && !declined_at && local_date <  today
approved?  = approved_at  && !reversed_at
reversed?  = approved_at  &&  reversed_at
declined?  = declined_at
#+end_src

The price snapshot is *non-negotiable*. The total is cumulative all-time and purely derived, so reading a live ~rewards.points~ at derivation time would make history mutable: a parent raising a reward's price would retroactively deepen every past spend of it and silently move a child's balance, potentially into debt after the fact. The snapshot is taken at *request* time for the kid leg — that is the deal the child was shown — and at redeem time for the parent-direct leg (SC-7).

A ~reward_name~ snapshot is deliberately *not* taken: reward rows are kept forever (archive, never delete), so the join is always available and the name stays a single source of truth. A rename is correctly reflected in history — a parent renaming a reward is clarifying what it is, not creating a different one.

*** Indexes

#+begin_src sql
-- one open request per kid per local day
CREATE UNIQUE INDEX redemptions_one_pending_per_kid
  ON redemptions (kid_id, local_date)
  WHERE requested_at IS NOT NULL AND approved_at IS NULL AND declined_at IS NULL;
#+end_src

The same partial-unique-index technique the shipped ~completions (chore_id, local_date) WHERE undone_at IS NULL~ index already uses. Including ~local_date~ in the key is what makes lapse *free*: yesterday's unanswered request cannot block today's, with no job and no cleanup (SC-6).

A racing duplicate hits the index and returns ~{:error, changeset}~, which callers treat as already-asked — the same posture ~complete_chore/3~ takes on a racing double-tap.

Supporting indexes on ~redemptions (reward_id)~ and ~(kid_id, local_date)~ serve the availability and balance reads.

** Availability and repeatability

Availability is *fully derived* from existing redemption rows. Nothing is stored, no job runs, and the next local day arriving is what restores a repeatable reward — exactly the D10 mechanism by which a completed chore becomes incomplete at midnight.

Both predicates are *scoped per-kid*. ~kid_id~ on a reward is an audience control — who the reward is offered to — and carries no scarcity meaning whatever.

Let ~spends(reward, kid)~ be the redemption rows for that reward /and that kid/ with ~approved_at IS NOT NULL AND reversed_at IS NULL~.

#+begin_src
one-time  (repeatable = false):
  consumed?     = spends(reward, kid) is non-empty     -- this kid, ANY day
  available?    = not consumed?

repeatable (repeatable = true):
  on_cooldown?  = spends(reward, kid) has a row with local_date = today
  available?    = not on_cooldown?
#+end_src

One uniform scope, one mental model: *every availability question is asked about one kid at a time.* "One-time" means /each kid may claim it once, ever/; "repeatable" means /each kid may claim it once per day/ (SC-5). Whether a reward is offered to one kid or to both changes nothing about how either predicate evaluates — ~kid_id~ decides *who sees it*, never *how many exist*.

A reversal *restores availability for free*. Both predicates exclude reversed rows, so a parent reversing a redemption returns a one-time reward to that child's catalog and clears a repeatable reward's cooldown, with no extra code path (SC-8).

Pending requests *do not consume*. A pending row has no ~approved_at~, so it is invisible to both predicates. Under per-kid scoping there is *no cross-kid race to close*: two kids holding pending requests for the same reward is simply two independent asks, and both may legitimately be approved.

A *same-kid* interleaving does remain possible, and it is why the approval-time re-check validates availability as well as affordability: a child asks for a reward on the kiosk, the parent direct-redeems that same reward for that same child from admin, and then approves the still-open request — which would claim a one-time reward twice, or a repeatable one twice in a day. The re-check catches it and tells the parent which check failed.

Card state is *always evaluated for the kid whose column it is*. With both predicates per-kid this is trivially true rather than an invariant needing maintenance: nothing on a child's shelf can change because of something the sibling did.

The one-open-request index *does not interact with any of this*. Its key is ~(kid_id, local_date)~ with no reward component, so it constrains *how many asks a kid has open*, never *which reward they may ask for*. Repeatability, kid scoping, and the open-request cap are three independent constraints.

** Affordability — strict on both legs

One rule, one function, both legs:

#+begin_src
Points.balance(kid, today) >= reward.points
#+end_src

The *true signed sum*, never the floored display figure — D41 pre-authorizes this in as many words. There is no parent override and no IOU concept: a parent's direct-redeem is bound by exactly the same check as a child's request (SC-4).

Checked twice:

1. *At request time* (kiosk) — an unaffordable reward renders visibly locked and is not tappable, so the check is a rendering rule before it is a validation.
2. *At approval time* (admin) — affordability *and* availability are re-validated, because the balance and the catalog both move between ask and answer.

Pending requests *contribute nothing*. A pending request contributes 0 to the balance and has no effect on the total, the badge, or affordability. There is no reserve or hold: escrowing a pending request's price against the balance would create two balances (true and available) that the always-visible badge (D43) cannot show at once. The race it would close — a child asking for two things they can only afford one of — is closed instead by the approval-time re-check plus the one-open-request-per-kid index, at zero display cost.

** Live updates

~BearCub.Rewards~ owns PubSub topic ="rewards"= and broadcasts a payload-free ~:rewards_changed~ on every successful write. ~KioskLive~ and ~Admin.TodayLive~ subscribe to it *in addition to* ="chores"=, and re-fetch — never patching from a payload.

This is the shipped ~Calendars.subscribe/0~ / ~:calendars_changed~ shape exactly: ~KioskLive~ already handles two independent topics with two ~handle_info/2~ clauses, so the pattern costs one clause per subscriber and introduces nothing new.

** Contexts and dependency direction (excerpt)

~BearCub.Rewards~ — a context owning the ~rewards~ and ~redemptions~ tables, the request / approve / decline / direct-redeem / reverse write paths, the availability derivation, and its own PubSub topic. It knows nothing about chores or completions.

#+begin_src
Points.balance = Chores.earnings + Rewards.spend_total
                 └─ D42's completions_earnings   └─ D42's other_signed_inputs
#+end_src

*Redemptions* — one aggregate summing ~points~ over rows with ~approved_at IS NOT NULL AND reversed_at IS NULL~, grouped by ~kid_id~.

** Testing (excerpt)

- *Unit* — redemption contribution across all marker combinations; the pending / lapsed / approved / reversed / declined derivations; one-time consumption and repeatable cooldown, both at per-kid scope — including a sibling's redemption of the same reward leaving this kid's card untouched, and the reversal-restores-availability path; affordability against a negative true balance.

- *Time* — every test pins ~:routine_windows~ per ~docs/learnings.org~ [2026-07-17] rather than inheriting the wall clock, and all new derivations take a local-date argument. Day-rollover behavior (lapse, cooldown reset, verdict-state expiry) is tested by *passing a different local date*, never by mocking a clock.

* User Story

As a parent, I need the rules of the reward economy — what exists, who may claim it, how often, what it costs, and what a request or a spend means — to be enforced in one place that the kiosk and admin both read, so that no surface can grant a reward a child cannot afford or has already claimed.

* Technical Notes

The Design excerpt above is the source of truth; DESIGN.org is broader context.

- Depends on Story 01 (the ~Points~ module affordability reads through) and Story 02 (the aggregate shape the redemptions leg joins). This story adds the third grouped query — the redemptions aggregate — alongside the table it reads.
- *The pins are the contract.* The summation changes again here when the third leg lands, so the Story-01 pinning suite binds this story exactly as it binds Story 02: if a pin fails, the change is wrong — do not adjust the pin. Editing a pin to accommodate the new leg is the smuggled semantic change D72 forbids. With the ~redemptions~ table empty the pins hold trivially, which is the point: nothing about earnings may move when the spend term arrives.
- Scaffold with ~mix phx.gen.context~ / ~mix ecto.gen.migration~ per repo convention, then reshape toward the design; do not hand-roll the context, migration, or PubSub wiring the generators provide.
- ~BearCub.Rewards~ must not reference ~BearCub.Chores~ or ~BearCub.Points~ in either direction of the dependency the design fixes: ~Points~ composes ~Chores~ and ~Rewards~; ~Rewards~ knows neither. Affordability lives where the composition lives, so the write paths that need it take the balance (or call through ~Points~ from the boundary) rather than teaching ~Rewards~ about earnings — settle this at implementation and record the shape in the story LOGBOOK.
- ~kid_id~ (both tables) and every timestamp marker are set programmatically and excluded from ~cast/2~, matching the shipped ~create_chore/2~ and ~Completion~ treatment.
- The racing-duplicate path is the same posture ~complete_chore/3~ takes: let the partial unique index raise the constraint error, convert it to ~{:error, changeset}~, and let the caller read it as already-asked.
- SQLite partial indexes: express the ~WHERE~ clause via ~create index(..., where: ...)~; verify the generated DDL matches the design's SQL, including that ~local_date~ is part of the key.
- Test the sibling case explicitly — a sibling's approved redemption of a shared reward must leave this kid's availability untouched — and the reversal-restores-availability path for both ~repeatable~ values.
- The design's "checked twice" is one function called from two places; do not write a second affordability rule for the parent leg.
- No UI in this story. The catalog screen is Story 04, the kiosk shop Story 05, the approval queue and reversal Story 06, and history Story 07 — but the write paths they all call land here, fully tested, first.
