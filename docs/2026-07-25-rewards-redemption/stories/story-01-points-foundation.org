* Design

** Contexts and dependency direction

Two new modules.

~BearCub.Rewards~ — a context owning the ~rewards~ and ~redemptions~ tables, the request / approve / decline / direct-redeem / reverse write paths, the availability derivation, and its own PubSub topic. It knows nothing about chores or completions.

~BearCub.Points~ — a composition module, the only place in the app that knows both earnings and spends:

#+begin_src elixir
Points.balance(kid, local_date)   # raw signed integer; may be negative
Points.total(kid, local_date)     # max(0, balance) — the D41 display figure
Points.balances(local_date)       # %{kid_id => signed} for a whole render
Points.totals(local_date)         # %{kid_id => floored} for a whole render
#+end_src

~Chores.points_total/2~ becomes ~Chores.earnings/2~ and returns the *raw signed* earnings, unfloored — the floor moves up to ~Points~, where the complete summation lives. ~Chores~ never learns that ~Rewards~ exists.

#+begin_src
Points.balance = Chores.earnings + Rewards.spend_total
                 └─ D42's completions_earnings   └─ D42's other_signed_inputs
#+end_src

Cost to shipped code, stated plainly: the kiosk's ~points: Chores.points_total(kid, today)~ call, admin balance reads, and the existing points-derivation tests all move to ~Points~. This is a rename plus a re-point, not a rewrite, and the aggregate rewrite touches the same function anyway.

** From the Overview

Redemption also makes the points total load-bearing: it is read on every reward-card render, on every tap that checks affordability, and on every admin balance display. The shipped ~points_total/2~ issues on the order of one query per routine-day of history, which is why PRD SC-9 requires the check be cheap and /stay/ cheap as months accumulate. The deferred aggregate rewrite is therefore claimed here as a batch member and lands early, before affordability depends on it — as a pure performance refactor with semantics provably unchanged.

** From the points aggregate rewrite — the pinning requirement

Discovered property — *roster drift*, surfaced but not fixed: ~routine_day_contribution/3~ loads the kid's *current* chore roster for the routine and requires every one of those chores to have a live completion on the evaluated date. Historical routine-days are therefore evaluated against today's roster: adding a morning chore today retroactively makes every past morning-day incomplete, wiping all historical ~+R~; deleting one can retroactively complete past days and grant points that were never earned. This ships today, and the badge already moves when a parent edits chores. Redemption raises the stakes: a roster edit can move a balance *after* a spend, potentially into debt with no fail involved.

Semantics stay *unchanged* in the rewrite — it is a pure performance refactor, proven behavior-preserving by tests — and roster drift is captured as its own backlog entry at initiative close. The claimed item is the query shape, not the derivation's semantics.

The pinning tests *must include a roster-drift case* — a routine-day evaluated after the roster changed — so behavior preservation is proven on the weird path and not merely the happy one. A refactor that silently "fixed" drift would be an unruled semantic change smuggled in under a performance story.

* User Story

As the parent maintaining this app, I need the points total to live behind one composition module with its current behavior captured as tests, so that the affordability rule about to be built on top of it reads from a single honest source, and the performance rewrite that follows can be proven to have changed nothing.

* Technical Notes

The Design excerpt above is the source of truth; DESIGN.org is broader context.

- No dependencies on earlier stories in this batch — this is the batch's first story. Story 02 depends on it: the pinning suite is the baseline proof that the aggregate rewrite preserves behavior, so it must exist first.
- The pinning suite is *this story's primary deliverable*. It is not incidental test coverage: Story 02's rewrite is accepted or rejected against it, and per D72 it must pass unmodified there.
- ~Points.balances/1~ and ~totals/1~ may be implemented in this story as a straightforward per-kid loop over the existing derivation — the point of this story is the module boundary, the rename, and the pins. The grouped-query rewrite behind the same signatures is Story 02.
- The rename is a rename plus a re-point, not a rewrite: ~Chores.earnings/2~ keeps the shipped derivation body, minus the ~max(0, …)~ wrapper which moves up to ~Points.total/2~.
- Roster drift is *pinned, not fixed*. If the pinning test's expected value looks wrong, that is the point — write the value the shipped code actually produces and leave a comment naming it as the D72 roster-drift case. Do not repair it here or in Story 02; it is a backlog entry at initiative close.
- LiveView surfaces are touched only insofar as they call the renamed function; no user-visible flow changes, so no new integration tests are owed beyond keeping the shipped ones green.
