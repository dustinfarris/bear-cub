- History pagination (D70) — the list is bounded at 50 with the bound stated on screen; pagination is a backlog seed if it ever bites.
- Wall-clock-derived date argument in a pre-existing admin test (Story 01) — /a fail live-updates the kiosk: the chore reverts and the points badge drops/ in ~test/bear_cub_web/live/admin/today_live_test.exs~ passes ~DateTime.to_date(LocalTime.now())~ as its local date. This is *not* a ~docs/learnings.org~ [2026-07-17] violation — that test does pin ~:routine_windows~, which is what the learning actually requires — but the date argument itself is still read from the wall clock rather than passed in, so the test exercises whichever local date the run happens to land on. A test-hygiene seed: the [2026-07-17] discipline applied retroactively to a date argument the learning did not reach. Swept to ~docs/backlog.org~ at initiative close.
- No automated guard on the ~Chores~ ⇏ ~Rewards~ dependency direction (Story 01) — CLAUDE.md treats this as a design invariant alongside ~Chores~ ⇏ ~Calendars~, and [[file:../decisions.org::#d57][D57]] rests on it: the moment ~Chores~ imports ~Rewards~, a rewards failure can reach the chore path. Today it holds by convention and by ~grep~ at review time; nothing fails if a future session wires the two together. A durable guard — a boundary test, or a compile-time check over the module's references — is a seed, not this initiative's work: it would need its own ruling on instrument and placement, and it applies to the older ~Calendars~ invariant just as much. Swept to ~docs/backlog.org~ at initiative close.
- SQLite sandbox-teardown log noise (Story 01) — *checked against the ledger, no new entry owed.* ~mix precommit~ emits ~Exqlite.Connection … disconnected~ ~[error]~ lines from LiveView sandbox teardown; confirmed pre-existing on a stashed baseline. ~docs/backlog.org~ already carries "Test-teardown Exqlite disconnect log noise — act only if log-clean output becomes a goal", whose surviving trigger after the [2026-07-24] ~BearCub.MigrationTestRepo~ removal is precisely the ~today_live_test.exs~ cross-process PubSub test — the same trigger Story 01 observed. No new information, no duplicate entry, following the same fold-in the gamification batch's Story 10 made.
- ~mix ecto.reset~ seeds the test database when run under ~MIX_ENV=test~ (Story 02) — the alias chains ~ecto.drop~ → ~ecto.setup~, and ~ecto.setup~ unconditionally runs ~priv/repo/seeds.exs~; there is no ~MIX_ENV~ guard distinguishing "reset my dev sandbox" from "reset the test database a suite is about to run against." Run against ~MIX_ENV=test~, it permanently inserts the placeholder ~"Kid A"~/~"Kid B"~ rows (and demo chores) directly into the test db file, outside any ~Ecto.Adapters.SQL.Sandbox~ transaction — the seeded rows survive every subsequent ~mix test~ invocation (the ~test~ alias's own ~ecto.create --quiet~/~ecto.migrate --quiet~ are no-ops against an already-existing, already-migrated db) until the file is manually dropped and recreated without seeding. Discovered when Story 02's own verification loop hit this by accident, producing a run of failures (leaked kid/chore rows, id drift, a "fresh production database" test finding kids present) that reproduced identically against a ~git stash~ of pre-story code, ruling out the rewrite as the cause. Fix used at the time: ~MIX_ENV=test mix ecto.drop && MIX_ENV=test mix ecto.create && MIX_ENV=test mix ecto.migrate~ (skipping ~ecto.setup~'s seed step). A durable fix — guarding ~ecto.setup~'s seed step on ~Mix.env() == :dev~, or splitting ~ecto.setup~ into a seeding and non-seeding variant — is a backlog seed, not this initiative's work: it touches shared tooling (~mix.exs~) rather than any one story's code.
- A late approval retroactively changes an earlier historical balance read (Story 03) — *narrowed by [[file:../decisions.org::#d73][D73]]'s day-scoped ~check_open/2~.* ~Rewards.spend_totals_by_kid/1~ filters on a redemption row's ~local_date~ (request time) combined with its *current* ~approved_at~/~reversed_at~ state, not the state as of the date being queried, so a marker stamped after the fact changes what an earlier "as of" read reports. The original multi-day form — request day 1, ~Points.balance(kid, day2)~ read before approval, approve on day 3, the same read afterward returns a lower figure — is now closed at the write layer: ~approve_redemption/3~ refuses a request once its ~local_date~ is before today, so no ordinary write path can approve a day-1 request on day 3. What remains, still D72-class ([[file:../decisions.org::#d72][D72]]): (a) the *same-day* cumulative-read case — a request and its approval both dated today, with an intermediate ~Points.balance~ read taken between the two, still moves after the fact, since ~check_open/2~ only excludes prior days, not same-day timing; (b) direct data manipulation (IEx, or any future admin action that stamps ~approved_at~ outside the guarded write paths) can still produce a lapsed-then-approved row, bypassing the guard entirely. Both are accepted under the same reasoning D72 already was, not fixed inline. Swept to ~docs/backlog.org~ at initiative close alongside the roster-drift entry.
