* Roster drift (D72) — ~chores.inserted_at~-bounded roster handles additions but not deletions
:PROPERTIES:
:CREATED:  [2026-07-25 Sat 22:40]
:END:
~routine_day_contribution/3~ (now composed into ~Chores.routine_days_by_kid/1~, the rewards/redemption Story 02 grouped-query rewrite) evaluates historical routine-days against the kid's *current* chore roster: adding a morning chore today retroactively makes every past morning-day incomplete, wiping historical ~+R~; deleting one can retroactively complete past days and grant points never earned. Needs its own ruling: a ~chores.inserted_at~-bounded roster (scoring a historical day against the roster live *on that day*, not today's) would handle additions correctly but not deletions, since a deleted chore leaves no row left to bound against. Not designed for in the rewards/redemption initiative.

* ~mix ecto.reset~ seeds the test database when run under ~MIX_ENV=test~ :oneshot:
:PROPERTIES:
:CREATED:  [2026-07-25 Sat 22:40]
:END:
The ~ecto.reset~ alias (~mix.exs~) chains ~ecto.drop~ → ~ecto.setup~, and ~ecto.setup~ unconditionally runs ~priv/repo/seeds.exs~ — there is no ~MIX_ENV~ guard distinguishing "reset my dev sandbox" from "reset the test database a suite is about to run against." Run against ~MIX_ENV=test~, it permanently inserts the placeholder kid/chore rows directly into the test db file, outside any ~Ecto.Adapters.SQL.Sandbox~ transaction — the seeded rows survive every subsequent ~mix test~ invocation until the file is manually dropped and recreated without seeding (~MIX_ENV=test mix ecto.drop && MIX_ENV=test mix ecto.create && MIX_ENV=test mix ecto.migrate~, skipping ~ecto.setup~'s seed step). Discovered when rewards/redemption Story 02's own verification loop hit this by accident (a run of failures — leaked kid/chore rows, id drift, a "fresh production database" test finding kids present — reproduced identically against a ~git stash~ of pre-story code, ruling out the rewrite as cause). A repo-tooling oneshot: guard ~ecto.setup~'s seed step on ~Mix.env() == :dev~, or split ~ecto.setup~ into seeding and non-seeding variants. Touches shared tooling (~mix.exs~), not any one story's code.

* TODO [#C] Kiosk collapse-delay can double-schedule its collapse timer on a rapid undo/redo :oneshot:
:PROPERTIES:
:CREATED:  [2026-07-18 Sat 23:35]
:END:
~BearCubWeb.KioskLive~'s collapse-delay (~lib/bear_cub_web/live/kiosk_live.ex~, Story 07): a rapid undo/redo of a routine's last chore within the ~@collapse_delay_ms~ (400ms) window can schedule more than one ~Process.send_after(self(), {:collapse_ready, kid_id}, ...)~ for the same kid — the first timer's reference is never stored or cancelled on undo. The extra message is a harmless no-op (~MapSet.delete~ on an already-absent key, then an idempotent reload), so no incorrect UI state results, but a very fast undo→redo could make the band appear slightly earlier than a full fresh delay after the final completion. Not covered by any AC — the design's "short delay" is explicitly imprecise at this level.
